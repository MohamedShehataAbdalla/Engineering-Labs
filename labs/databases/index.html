معمل Databases: الداتا بتتخزن وتتقري إزاي فعلًا

السيناريو ثابت في المعمل كله: 10,000 جهاز GPS كل واحد بيبعت موقعه كل 10 ثواني، يعني 1,000 insert في الثانية في جدول GpsPoints(Id, VehicleId, Ts, Lat, Lng, Speed). كل تجربة بتوريك جزء من اللي بيحصل جوه SQL Server وأنت بتكتب وتقرا الجدول ده. الحركة متبطّأة عشان عينك تلحقها.

صف أو طلب جديد داخل داتا متخزنة أو شغل خلص metadata: header، slot array، index كويس / سريع مكلف: split، scan، ضياع

التخزين والـ Indexes

Storage & Indexes

Page / Row / Page Split / FILLFACTOR / Fragmentation

أساسي

نقط الـ GPS بتتكتب كصفوف جوه صفحات 8 KB. فوق: تشريح آخر صفحة اتكتب فيها. تحت: كل صفحات الجدول بترتيب الـ key، والجزء الملوّن هو نسبة امتلاء كل صفحة.

الـ Clustered key
حجم الصف شامل الـ overhead

الفكرة

SQL Server مش بيقرا ويكتب صفوف، بيقرا ويكتب Pages. كل صفحة 8 KB (8,192 bytes): أول 96 byte header، وبعدين الصفوف، وفي آخر الصفحة slot array (2 bytes لكل صف) بيقول كل صف موجود فين. كل 8 صفحات بيكوّنوا Extent (64 KB).

لو الجدول عليه clustered index، صفوفه مترتبة منطقيًا بالـ key. لو صف جديد لازم يدخل صفحة مليانة، بيحصل Page Split: حوالي نص الصفوف بيتنقل لصفحة جديدة. FILLFACTOR نسبة الملء وقت بناء الـ index، عشان يفضل مكان للـ inserts الجاية. Fragmentation معناها إن ترتيب الصفحات المنطقي بقى مختلف عن ترتيبها على الديسك.

مثال من الواقع

جدول GpsPoints بياخد 1,000 insert في الثانية. لو الـ clustered key هو Id IDENTITY، كل الكتابة بتروح لآخر صفحة، والصفحات بتتملي 100% من غير splits. لو هو NEWID()، كل صف بيقع في مكان عشوائي، فالـ splits مبتقفش والصفحات بتستقر حوالي 69% مليانة. يعني نفس الداتا بتاخد صفحات أكتر بحوالي 45%، وده IO وذاكرة أكتر في كل قراءة.

قارن IDENTITY و NEWID() في Page density والـ Fragmentation. بعدين خلّي FILLFACTOR = 70 واضغط REBUILD: الـ splits هتختفي فترة لحد ما الفراغ يتملي وبعدين ترجع. وجرّب صف 4100 B: صف واحد بس يدخل الصفحة، ونصها بيفضل فاضي على طول.

بوابات الدفع والبنوك (TransactionId من نوع GUID)، والشات (MessageId)، وطلبات منصات التوصيل.

في .NET و SQL Server

-- key متزايد: الكتابة كلها في آخر صفحة
CREATE TABLE GpsPoints (
  Id BIGINT IDENTITY PRIMARY KEY CLUSTERED,
  VehicleId INT NOT NULL, Ts DATETIME2(0) NOT NULL,
  Lat DECIMAL(9,6), Lng DECIMAL(9,6), Speed SMALLINT);

-- اترك 10% فاضي في كل صفحة
ALTER INDEX ALL ON GpsPoints
  REBUILD WITH (FILLFACTOR = 90);

-- قيس الامتلاء والـ fragmentation
SELECT avg_page_space_used_in_percent,
       avg_fragmentation_in_percent, page_count
FROM sys.dm_db_index_physical_stats(
  DB_ID(), OBJECT_ID('GpsPoints'), NULL, NULL, 'SAMPLED');
// EF Core: الـ long key بيتعمل IDENTITY تلقائيًا
modelBuilder.Entity<GpsPoint>()
    .HasIndex(p => new { p.VehicleId, p.Ts });
أعمق (للـ Senior)
  • المشكلة التانية للـ IDENTITY: كل الـ threads بتكتب في نفس آخر صفحة، فبيحصل contention على الـ latch بتاعها (PAGELATCH_EX) لما الحمل يبقى عالي. من SQL Server 2019 فيه OPTIMIZE_FOR_SEQUENTIAL_KEY = ON على الـ index بيخفف ده.
  • ليه 70% بالذات؟ مع inserts عشوائية و split نص بنص، متوسط امتلاء الـ B-tree بيستقر حوالي ln 2 ≈ 69%. ده نتيجة رياضية معروفة، وهتشوفها بتطلع لوحدها في المحاكاة.
  • (VehicleId, Ts) بيخلّي «مسار عربية في يوم» صفحات جنب بعض، فالقراءة سريعة جدًا. التمن إن الكتابة بتعمل splits في نص الـ index. فيه تصميم شائع: clustered على Id للكتابة، و non-clustered على (VehicleId, Ts) للقراءة. التجربة الجاية بتقيس الفرق ده.
  • GUIDs: EF Core بيولّد للـ Guid keys قيم sequential من ناحية العميل (SequentialGuidValueGenerator) عشان يقلل الـ splits. لكن خد بالك: Guid.CreateVersion7() (.NET 9) مترتب بالوقت، بس SQL Server بيقارن الـ uniqueidentifier بآخر 6 bytes الأول، فـ UUIDv7 بيتصرف في الـ clustered index قريب من الـ NEWID.
  • الـ split مكلف في الـ log: نقل الصفوف لصفحة جديدة بيتسجل كله في الـ transaction log، فالـ mid-page split بيولّد log أكتر بكتير من insert عادي.
  • Fragmentation مقابل Density: على SSD تأثير الترتيب على الديسك أقل من زمان، لكن الـ density مهمة دايمًا: صفحات أكتر يعني buffer pool أكبر و IO أكتر لنفس عدد الصفوف.
  • ترتيب الصفوف جوه الصفحة بيحفظه الـ slot array، مش مكان الصف نفسه. عشان كده الصف الجديد بيتكتب في آخر الجزء المستخدم (البرتقالي في الرسم) حتى لو الـ key بتاعه في النص.
  • تبسيطات في المحاكاة: بنعمل الـ split نص بنص بعدد الصفوف، و SQL Server الحقيقي بيختار نقطة التقسيم بالحجم ومكان الـ insert، فالنتيجة «تقريبًا نص بنص». حجم الصف ثابت، وأقصى صف in-row في الحقيقة 8,060 bytes.
